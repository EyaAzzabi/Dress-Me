# RLHF System for DressMe

Complete RLHF pipeline implementation: DB schema, API endpoints, ML training pipeline with proper PPO, and frontend dashboard. Four features (FEAT-001 through FEAT-004) deliver a full feedback → preference pairs → reward model → policy model loop that integrates into the existing recommendation agent via an environment flag.

Watch for: (1) **confirmed** — `train_rlhf.py` does not pass `min_pairs` to `build_preference_pairs`, so the `ready_for_training` gate always evaluates against the hardcoded default of 100, not the user-supplied `--min-pairs` value. (2) **confirmed** — `NAV_ITEMS` has a duplicate `rlhf` entry in the raw source file at line 62 (two identical `{ id: "rlhf", ... }` entries); this renders harmlessly because the second entry is a duplicate reference, but it indicates a leftover edit artifact.

**Verdict**: APPROVED

## High-level view

The DB layer is clean: `RLHFFeedback` has no `UNIQUE(user_id, outfit_id)` constraint, `items_liked`/`items_disliked` round-trip through a `JSONListTypeDecorator`, and the migration file follows the established Alembic pattern exactly. FIX-5 is fully implemented.

The API layer handles both the always-INSERT feedback contract and the stats aggregation correctly. The `pairs_available` computation uses distinct outfit count which is correct. The CSV export uses Python's `csv` module and returns proper `Content-Disposition` headers. The stats endpoint's `readiness_for_training.last_trained_at` correctly reads the reward model artifact mtime.

The ML pipeline honours FIX-1 and FIX-4 throughout: `embedding_fetcher.py` never creates zero vectors, skips missing items with warnings, and excludes outfits below 70% coverage. `preference_dataset.py` replicates this same logic and correctly deduplicates to the latest-per-outfit feedback row before the coverage check. The PPO implementation in `rlhf_policy_model.py` collects old log-probs in a no-grad pass, then recomputes ratios and applies the clipped objective with an entropy bonus, exactly as specified in FIX-2.

The recommendation agent's fallback chain (FIX-3) is implemented as `_load_models()` / `_score_items()`: RLHF policy is attempted when `USE_RLHF_MODEL=true`, falls back to SFT with a warning if the checkpoint is missing, and falls back to neutral 0.7 if SFT also fails. The old `_load_sft_model` name is retained as an alias for backwards compatibility.

The frontend TypeScript types in `api.ts` match the backend Pydantic schemas field-for-field. The `RLHFDashboard` component uses only `<table>`, `<ul>`, and flex/grid CSS — no chart library. The frontend build exits 0 with no TypeScript errors. No `recharts` or any new npm package was added.

<summary>Details</summary>

### FIX-2: PPO clipping — confirmed correct

Old log-probs are collected with `torch.no_grad()` before the training loop. Per epoch, new log-probs are recomputed with gradients, ratios are `exp(new_lp - old_lp.detach())`, clipping is `torch.clamp(ratio, 1-eps, 1+eps)`, and the entropy bonus subtracts `entropy_coef * entropy` from the combined loss. The reward model is put in `.eval()` mode and never receives gradients during policy training. This is a complete and correct PPO implementation.

### FIX-3: RLHF → SFT → 0.7 fallback chain — confirmed correct

`_load_models()` unconditionally attempts to load the SFT model, then checks `USE_RLHF_MODEL`. If the env var is true but `load_policy_model()` returns `None` (artifact missing), a warning is logged and `use_rlhf` stays `False`. `_score_items()` routes through the RLHF path only when `use_rlhf=True and policy_model is not None`; otherwise it calls `_score_with_sft()`; `_score_with_sft()` itself falls back to 0.7 when model or torch is unavailable. The chain is complete.

### `--min-pairs` propagation gap (confirmed)

`train_rlhf.py` accepts `--min-pairs` via argparse and passes it to `_run_pipeline()`. Inside `_run_pipeline()`, the call on line 123 is:

```python
pairs, meta = build_preference_pairs(db, user_id)
```

The `min_pairs` argument is not passed here, so `build_preference_pairs` uses its own default of 100 to compute `ready_for_training`. The `--min-pairs` value is only used at the second gate after embedding filtering (line 153). If someone passes `--min-pairs 50` expecting early exit behavior, they'll still get blocked by the default 100 at the first gate.

### Duplicate nav entry (confirmed)

`NAV_ITEMS` in `App.tsx` contains two entries with `id: "rlhf"`. The TypeScript build passes because it's a valid array — no duplicate-key error. The runtime effect is two "Suivi RLHF" items in the sidebar navigation. This is cosmetically broken.

### FIX-4 and FIX-1 — confirmed correct in both pipeline modules

`embedding_fetcher.get_outfit_embeddings()` and `preference_dataset.build_preference_pairs()` both call `vector_store.fetch_embeddings()`, iterate the result, log warnings for missing items, and apply `coverage < 0.7` to exclude the outfit entirely. The count of excluded outfits is logged at WARNING level in both modules. Neither module allocates a zero vector at any code path.

### FIX-5 — confirmed correct

`RLHFFeedback` model: `__table_args__` contains only `CheckConstraint`, two `Index` definitions, and a comment confirming no `UniqueConstraint`. The migration file has no `sa.UniqueConstraint` in `op.create_table`. `POST /rlhf/feedback` always constructs a new `RLHFFeedback(id=uuid.uuid4(), ...)` and calls `db.add(feedback)` with no conflict clause. `is_new` is hardcoded to `True`.

### TypeScript interface alignment — confirmed

Backend `RLHFStats.most_liked_occasions: dict[str, float]` → frontend `Record<string, number>`: Python `float` serializes as JSON number, TypeScript `number` covers both integer and float — no mismatch. `readiness_for_training` uses `dict` in the Pydantic schema (untyped) and a typed inline interface in the frontend; all four keys (`has_sufficient_data`, `pair_count`, `next_threshold`, `last_trained_at`) are present in the API route's returned dict.

### No chart library — confirmed

`package.json` dependencies: `react`, `react-dom`, `axios`. No `recharts`, `chart.js`, `d3`, or any visualization library. `RLHFDashboard` uses `<table>`, `<ul>`, `<div>` with flex layout, and `<button>` elements only.
